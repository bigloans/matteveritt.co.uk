Design systems · AI-assisted development

I replaced my own design system with one AI builds from

I built the component library behind 60+ products in React, Vue, Angular and legacy frameworks. The evidence said it couldn't keep up, so I replaced it with a versioned specification that teams' AI coding agents build from, and a gate that checks the result. I run it as a product: strategy, roadmap, releases and adoption are mine.

Customers

The customers and the product I'd built

My customers are the product teams behind 60+ products, working in React, Vue, Angular and legacy frameworks. Each team has its own roadmap, and none of them is waiting for a design system.

V1, THE LIBRARY I BUILT

45 components, with React, Vue and Angular built simultaneously. I delivered it against a roadmap in four stages that I presented at CTO level: audit and alignment, assets package and pipeline, component library build, then rollout and adoption.

TENURE

The problem

The evidence against my own library

Running the static gate against existing products found a median of 412 violations per product, mostly raw colour values. Each v1 component cost about 3.5 weeks across three framework builds, roughly two of them on the second and third builds. And nothing told an AI coding agent what on-brand or accessible meant.

Options

Three options, one decision

I judged each option on five criteria.

  • Framework coverage
  • Time to ship
  • Drift control
  • Maintenance cost
  • Dependence on a central team
OPTION A

Continue v1

Keep the library and its three framework builds.

Why it lost. Continuing v1 meant one person building every component three times, for low adoption.

OPTION B

Generate code from Figma

Generate components from Figma through a framework-agnostic JSON contract, the Component Schema Layer I piloted with Claude and Cursor.

Why it lost. Figma-to-code generates from a picture, so the rules never reach the code.

OPTION C · CHOSEN

Specify and verify

Write a specification that teams' agents build from, and a validation gate that checks the result. No library.

What the pivot cost

  • 45 components of v1 work, set aside
  • Teams who had only just migrated to v1
  • The v1 roadmap I had committed to at CTO level

How I handled it. The asset pipeline carried over intact. Teams who had migrated got a mapping from v1 tokens to the new semantic names. I re-presented the CTO roadmap with the same four stages and new milestones.

The product

Remove the library and keep the contract

The spec covers 21 components and 6 layout primitives. Before 1.0 I ship small and often, with 90 releases in 14 weeks. Teams pin a release, so nothing changes in a product until its team upgrades.

01

One spec, any framework

Tokens, component rules and the definition of done live in three plain-text files that work with React, Vue or plain HTML.

02

Accessibility lives in the tokens

Every colour pairing the system allows meets WCAG 2.2 AA in both themes, so the agent can't pick a failing pair. A failure blocks the release.

03

A release is a contract

Teams pin a tagged release, and a hash proves they built against exactly the spec they asked for.

Token format: the tokens live in the spec file, not in the W3C Design Tokens Community Group format. The consumer is an agent reading one file, and a JSON copy would be a second source to keep in step. If a tool ever needs that format, it gets a generated copy.

Visual language

Every visual choice is a rule the agent can follow

An agent can't interpret "make it feel premium". So I turned each aesthetic decision into a named rule with a token behind it. These are recreations of five of them.

Two themes

Brand energy where it counts

Dark is the signature theme, with deep navy, luminous teal and depth expressed through light. Light is the working surface, restrained and precise for dense enterprise workflows. The same tokens drive both.

AI disclosure, designed for regulation

The one component unique to this system marks content or actions produced by AI. It supports disclosure under Article 50 of the EU AI Act, which has applied since 2 August 2026. Machine-readable marking of generated content is a separate obligation the component doesn't cover.

The gate

Trust, but verify every change

A spec only works if someone checks it was followed. I built a validation gate with Claude Code that blocks any change that breaks the contract.

STATIC

Reads the source on every commit. It flags raw colours, off-scale spacing, unknown tokens, broken type pairings and CSS that would break right-to-left layouts.

RENDERED

Opens a real browser before merge. It measures contrast on the actual pixels in both themes, tabs through every control and checks for a visible focus ring.

HUMAN

Says where automation stops. A screen can pass the gate and still be the wrong screen. The adoption guide says so plainly, so reviewers spend their time there.

First evidence

First evidence: three AI builds found what review missed

Until then, the spec had only been checked by reading it. So I tested it the way teams would use it, by building from it.

01 · BUILD

Three fresh sessions

Each AI session got only the pinned spec and built the same components from scratch.

02 · MEASURE

Same failure, three times

All three failed the rendered gate on one button state. Every token was valid, so no static check could see it.

03 · FIX

Rule fixed, process changed

I corrected the rule. Any release that changes a rule now gets the same test.

Recreation. Ratios are calculated live from the colours shown. AA needs 4.5:1.

CAUGHT BY THE GATE

A rule that broke its own standard

The button rule gave its label 3.34:1 against 4.5:1 on its active surface. The same paragraph cited that ratio when it banned the pairing elsewhere. Reading missed it, but measuring the pixels didn't.

MISSED BY THE GATE

A rule that contradicted itself

A table rule asked for two things that can't both be true. The agent picked one and wrote clean code, and noted the conflict. So the release process now reads the agent's notes as well as the result.

n = 3 builds with one agent. In a rerun with Cursor, two of three builds passed first time. The third used an invented token name, which the gate caught and one iteration fixed.

Testing a spec by building from it finds defects that reading it misses. One defect across three runs supports the method; the model itself still needs adoption data.

Adoption

Adoption is the real test

Co-sponsored with the Head of UX. Engineering leadership made it the default for new UI and reskins, with no mandate to rewrite existing screens. The hardest audience was teams who had only just moved onto the previous version of the design system.

THE OBJECTION
Why redo work we've only just finished?

Those teams had spent real time on the last migration and didn't want to spend it again.

WHAT CHANGED THEIR MINDS
01

Speed

In pilots, a screen took a median of 1.5 days from the spec, against 5 through the old handoff. Most of the saving was handoff wait removed.

02

No cost to them

I built the first three implementations myself. From team four, teams self-serve with the one-command setup and a one-hour kick-off, reaching a first gate pass in a median of 2.5 days.

03

Proof from pilots

Nine pilots across React, Vue and Angular, from compliance and audit tools to an inspection app. A server-rendered legacy product reached its first screen.

THE OUTCOME
"We love it, but we can't do it right now."

Rollout follows each team's roadmap, so nobody migrates mid-delivery. The forcing function was a funded reskin already on the roadmap. The system rode along with work the team was doing anyway. Mandates and demos converted nobody.

Where I changed my mind

I argued rollout should wait until the component gap list closed. The evidence beat me. A smoke test found six contract defects that review had missed. Pilots started alongside the first component batch and became the main way we find defects.

“We stopped arguing about pixel values in review. The gate settles that, so review is about whether the screen works.”Front-end lead, pilot product

Adoption blockers

Every known blocker is a tracked issue.

  • Theme attribute. Solved, because the setup script sets it.
  • Custom-property collisions. Solved, because setup audits them and stops before linking.
  • One-way theming. Solved, because the dark override block shipped.
  • Legacy global CSS. Still needs human review. A box-sizing rule narrows the gap.

Trade-offs

What this approach costs, and how I contained it

The decision log records what each major choice costs. Here are six.

Cost

AI output varies from run to run

Three runs from an identical brief used the same tokens and values but structured the code differently, from 407 to 930 lines.

How I contained it

Govern the contract, not the code

The gate checks tokens, contrast and behaviour, which held steady. Snapshot tests would break with every spec or model change. Product teams own generated code like any other code. It goes through their pull requests and tests, with the gate in CI. I own the spec and the gate, never the code.

Cost

Draft assets can look finished

Letting designers place a draft pictogram keeps them moving, but a draft could ship by accident.

How I contained it

Make drafts impossible to miss

Every draft is marked in the code and listed by the gate on every run, with a link to its review.

Cost

Existing products weren't built for this

Most early adopters have a shipping product, its own CSS and a designer with expectations.

How I contained it

Write the guide for existing products first

The adoption guide names the four problems existing products hit, in the order they hit them. Angular and Vue adopt like React. Server-rendered legacy products adopt screen by screen, about 2 to 3 weeks to the first screen. Products that can't load a stylesheet can't adopt.

Cost

A corrected rule has to reach every product

When I fix a rule, products on older releases keep the old one until they upgrade.

How I contained it

Pin, gate and track the fix

Pinning makes each upgrade deliberate, and the gate checks every build against its pinned release. A fix reaches a tagged release in under one working day, and all three production products within 6 working days, set by each team's merge.

Cost

The gate can't prove complex widgets behave correctly

The gate checks tokens, contrast, focus and ARIA, but not whether a complex widget behaves as users expect.

How I contained it

Split the checks between gate and people

Six of the contracts are complex widgets. The gate checks all six for tokens, type scale and static ARIA, plus rendered checks for names, roles and text contrast. For the modal it also tests focus trap, Escape and focus return. People check the rest, such as announcement order, typeahead, arrow-key focus, sort announcements, dismissal and landmark structure. Non-text contrast stays a human check for all six.

Cost

The spec depends on today's agents

The spec is written for today's coding agents. A new model or vendor could read it differently.

How I contained it

Test on more than one agent

The spec is markdown and the gate is deterministic, so neither depends on a model. The only vendor-specific file is a short pointer block. A rerun with Cursor passed after one iteration.

Roadmap

Shipping a design system like software

A spec that teams build from has to be as dependable as code, so I release it like code.

Reflection

What I'd tell the next team

Test a spec by building from it

Careful reading missed a defect that three AI builds found on the first try. Now every release that changes a rule is tested that way.

Put guardrails where people work

Asking designers to memorise a style guide fails quietly. Building the rules into their AI session made the right path the easy one.

Remove the cost of saying yes

Teams liked the idea from the start. What won them over was knowing the implementation work wouldn't land on them.

Retire your own work when the evidence says so

I built the library, and the evidence said to retire it: a median of 412 violations per product and about 3.5 weeks per component. Sunk work is a poor reason to keep a product alive.
