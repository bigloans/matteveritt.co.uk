I replaced my own component library with a spec AI builds from

I built the component library for a portfolio of 60+ products. The evidence said it couldn't keep up, so I replaced it with a versioned specification that teams' AI coding agents build from, and a gate that checks the result. I run it as a product, and strategy, roadmap, releases and adoption are mine.

Tenure

The problem

The evidence against my own library

Running the static gate against existing products found a median of 412 violations per product. Over six years, 6 products adopted v1, to varying degrees, across three frameworks. Each v1 component cost about 3.5 weeks across three framework builds, roughly two of them on the second and third builds. And nothing told an AI coding agent what on-brand or accessible meant.

Options

Three options, one decision

I judged each option on five criteria.

  • Framework coverage
  • Time to ship
  • Drift control
  • Maintenance cost
  • Dependence on a central team
Option A

Continue v1

Keep the library and its three framework builds.

Why it lost. One person would build every component three times, for low adoption.

Option B

Generate code from Figma

Generate components from Figma through a framework-agnostic JSON contract I piloted.

Why it lost. It generates from a picture, so the rules never reach the code.

Option C, chosen

Specify and verify

A specification that teams' agents build from, and a gate that checks the result.

What the pivot cost

  • 45 components of v1 work, set aside
  • Teams who had only just migrated to v1
  • The v1 roadmap I had committed to at CTO level

How I handled it. The asset pipeline carried over intact, migrated teams got a v1 token mapping, and I re-presented the CTO roadmap with new milestones.

The product

Remove the library and keep the contract

The spec covers 21 components and 6 layout primitives, with 90 releases in 14 weeks before 1.0.

One spec, any framework

Tokens, component rules and the definition of done live in three plain-text files, for any framework.

Accessibility lives in the tokens

Every colour pairing the spec allows is tested against WCAG 2.2 AA in both themes, and a failing pair blocks the release. Test builds once caught a rule that broke this (see First evidence).

A release is a contract

Teams pin a tagged release, and a hash records exactly which spec they pinned. The gate checks every build against it.

Visual language

Every visual choice is a rule the agent can follow

An agent can't interpret "make it feel premium", so each aesthetic decision is a named rule with a token behind it.

Two themes

Brand energy where it counts

Dark is the signature theme. Light is the working surface. The same tokens drive both.

The gate

Trust, but verify every change

I built a gate with Claude Code that blocks any change that breaks the contract.

Static

Reads the source on every commit. It flags raw colours, off-scale spacing, unknown tokens, broken type pairings and right-to-left breakage.

Rendered

Opens a real browser before merge. It measures contrast on real pixels in both themes and tabs through every control.

Human

Says where automation stops. A screen can pass the gate and still be the wrong screen, so reviewers spend their time there.

First evidence: three AI builds found what review missed

Until then, the spec had only been checked by reading it. So I tested it by building from it.

Build

Three fresh sessions

Each session got only the pinned spec and built the same components.

Measure

Same failure, three times

All three failed the rendered gate on one button state that no static check could see.

Fix

Rule fixed, process changed

I corrected the rule. Every release that changes a rule now gets this test.

Ghost buttonActive state, as specified3.34:1Fails AA
Fix
Ghost buttonActive state, corrected5.17:1Passes AA

Recreation. Ratios are calculated from the colours shown. AA needs 4.5:1.

Caught by the gate

A rule that broke its own standard

The button rule gave its label 3.34:1 against 4.5:1 on its active surface, and the same paragraph cited that ratio to ban the pairing elsewhere.

Missed by the gate

A rule that contradicted itself

A table rule asked for two things that can't both be true. The agent picked one, wrote clean code and noted the conflict, so the release process now reads the agent's notes too.

n = 3 builds with one agent. A Cursor rerun passed two of three first time, and the gate caught an invented token in the third. This supports the method, but the model itself still needs adoption data.

Running a product with a team of one

I run a harness of 15 specialist agents, each with one job and a written standard. Agents land measurable work, but spec and release decisions stay with me. Any edit that moves a brand value stops until it is explained, and no bug is fixed until one agent reproduces it and another checks the fix.

Adoption is the real test

Co-sponsored with the Head of UX. Engineering leadership made it the default for new UI and reskins, with no mandate to rewrite existing screens.

The objection
Why redo work we've only just finished?

It came from teams who had only just moved onto v1.

What changed their minds

Speed

In pilots, a screen took a median of 1.5 days vs 5 through the old handoff. Most of the saving was handoff wait removed.

No cost to them

I built the first three implementations. Later teams self-serve with a one-command setup.

The outcome
"We love it, but we can't do it right now."

Rollout follows each team's roadmap. A funded reskin was the forcing function, and mandates and demos converted nobody.

  1. 9 piloted
  2. 6 committed with a date
  3. 3 in production on a pinned release, including the AI agent and home hub

Of about 60 teams, counted for the weekly report.

Where I changed my mind

I argued rollout should wait until the component gap list closed. Then a smoke test found six contract defects that review had missed, so pilots started with the first component batch and became our main way to find defects.

Every known adoption blocker is a tracked issue. Three are solved, and legacy global CSS still needs human review.

“We stopped arguing about pixel values in review. The gate settles that, so review is about whether the screen works.”Front-end lead, pilot product

Trade-offs

What this approach costs, and how I contained it

The decision log records what each major choice costs. Here are four.

Cost

AI output varies from run to run

Three runs from one brief used the same tokens and values but structured the code differently, from 407 to 930 lines.

How I contained it

Govern the contract, not the code

The gate checks tokens, contrast and behaviour, which held steady. Product teams own generated code through their own reviews and tests. I own the spec and the gate.

Cost

Existing products weren't built for this

Most early adopters have a shipping product, its own CSS and a designer with expectations.

How I contained it

Write the guide for existing products first

The adoption guide names the four problems existing products hit, in order. Server-rendered legacy products take about 2 to 3 weeks to a first screen.

Cost

The gate can't prove complex widgets behave correctly

It can't tell whether a complex widget behaves as users expect.

How I contained it

Split the checks between gate and people

For the six complex widgets, the gate checks tokens, ARIA, names, roles and text contrast, plus the modal's focus handling. People check behaviour such as announcement order and arrow-key focus.

Cost

Pinning slows critical fixes

Pinning protects teams from unplanned changes, so a critical fix waits for each team to update its pin. Tagging a fix takes under one working day, and reaching all three products took six working days. That time grows with every adopter.

How I contained it

Roadmap

Shipping a design system like software

A spec teams build from must be as dependable as code, so I release it like code.
