I replaced my own component library with a spec AI builds from

I built the component library for a portfolio of 60+ products. The evidence said it couldn't keep up, so I replaced it with a versioned specification that teams' AI coding agents build from, and a gate that checks the result. I run it as a product, and strategy, roadmap, releases and adoption are mine.

The problem

My first design system was a component library I built. It had 45 components, with React, Vue and Angular built simultaneously. I delivered it in four stages against a roadmap I presented at CTO level.

Running the static gate against existing products found hundreds of rule violations per product. Over six years, 6 products adopted it, to varying degrees, across three frameworks. Each of its components cost about 3.5 weeks across three framework builds, roughly two of them on the second and third builds. And nothing told an AI coding agent what on-brand or accessible meant.

Before

  1. Designer draws the component
  2. Handoff to engineering 1 to 2 week wait
  3. Central team builds and releases 4 to 6 week wait
  4. Product team adapts it
  5. Accessibility audit

After

  1. Team pins a release of the spec
  2. Their AI agent reads the contract
  3. Agent generates the UI
  4. The gate checks it in CI
  5. People review what machines can't judge

Drift: static gate on the 12 pilot products, mostly raw colour values, then off-scale spacing. Durations: delivery history of the first design system.

Options

I judged three options on five criteria: framework coverage, time to ship, drift control, maintenance cost and dependence on a central team.

Option A

Keep the first design system

Keep the library and its three framework builds.

Why it lost. One person would build every component three times, for low adoption.

Option B

Generate code from Figma

Generate components from Figma through a framework-agnostic JSON contract I piloted.

Why it lost. It generates from a picture, so the rules never reach the code.

Option C, chosen

Specify and verify

A specification that teams' agents build from, and a gate that checks the result.

What the pivot cost

  • 45 components of work on the first design system, set aside
  • Teams who had only just migrated to it
  • Its roadmap, which I had committed to at CTO level

How I handled it. The asset pipeline carried over intact and migrated teams got a token mapping from the first system. I re-presented the CTO roadmap with new milestones.

What I built

The spec covers 21 components and 6 layout primitives, with 90 releases in 14 weeks before 1.0.

One spec, any framework

Tokens, component rules and the definition of done live in three plain-text files.

Accessibility lives in the tokens

Every colour pairing the spec allows is tested against WCAG 2.2 AA in both themes, and a failing pair blocks the release.

A release is a contract

Teams pin a tagged release, and a hash records exactly which spec they pinned. The gate checks every build against it.

Read a spec excerpt on focus rings

Each visual choice is a named rule with a token behind it. Visual rules an AI agent can follow shows how.

The gate

I built a gate with Claude Code that blocks any change that breaks the contract.

  1. Static

    Reads the source on every commit. It flags raw colours, off-scale spacing, unknown tokens, broken type pairings and right-to-left breakage.

  2. Rendered

    Opens a real browser before merge. It measures contrast on real pixels in both themes and tabs through every control.

  3. Human

    Says where automation stops. A screen can pass the gate and still be the wrong screen, so reviewers spend their time there.

See a real gate run

First evidence

I had only checked the spec by reading it, so I tested it by building from it.

  1. Build

    Three fresh AI sessions got only the pinned spec and built the same components.

  2. Measure

    All three failed the rendered gate on one button state no static check could see.

  3. Fix

    I corrected the rule, and every release that changes a rule now gets this test.

Caught by the gate

A rule that broke its own standard

The button rule gave its label 3.34:1 against 4.5:1 on its active surface, and the same paragraph cited that ratio to ban the pairing elsewhere.

Missed by the gate

A rule that contradicted itself

A table rule asked for two things that can't both be true. The agent picked one, wrote clean code and noted the conflict, so the release process now reads the agent's notes too.

n = 3 builds with one agent. A Cursor rerun passed two of three first time, and the gate caught an invented token in the third. This supports the method, but the model itself still needs adoption data.

Adoption

Engineering leadership made the spec the default for new UI and reskins, with no mandate to rewrite existing screens.

Why redo work we've only just finished?

Teams who had only just moved onto the first design system

What changed their minds

Speed

In pilots, a screen took a median of 1.5 days vs 5 through the old handoff, across 5 screens built both ways. Most of the saving was handoff wait removed.

No cost to them

I built the first three implementations. Later teams self-serve with a one-command setup.

The outcome was “We love it, but we can't do it right now.” Rollout follows each team's roadmap. A funded reskin was the forcing function, and mandates and demos converted nobody.

  1. 9piloted
  2. 6committed with a date
  3. 3in production on a pinned release, including the AI agent and home hub

Of about 60 teams, counted for the weekly report.

Designers now build in the same session as the agent. So far, 7 designers have contributed 47 catalogue entries, and Running a design system with 15 agents shows how.

Where I changed my mind

I argued rollout should wait until the component gap list closed. Then a smoke test found six contract defects review had missed, so pilots started with the first component batch and became our main way to find them.

We stopped arguing about pixel values in review. The gate settles that, so review is about whether the screen works.

Trade-offs

The decision log records what each major choice costs.

AI output varies from run to run

Cost

Three runs from one brief used the same tokens and values but structured the code differently, from 407 to 930 lines.

Contained by governing the contract, not the code

The gate checks tokens, contrast and behaviour, which held steady. Product teams own generated code through their own reviews and tests.

Existing products weren't built for this

Cost

Most early adopters have a shipping product, its own CSS and a designer with expectations.

Contained by writing the guide for existing products first

It names the four problems they hit, in order. Server-rendered legacy products take about 2 to 3 weeks to a first screen.

Pinning slows critical fixes

Cost

Pinning protects teams from unplanned changes, so a critical fix waits for each team to update its pin. That wait grows with every adopter.

Contained by updating pins through automated pull requests

Every tagged fix opens one for each adopter. Teams still review and merge it, so the pin keeps protecting them.

Reflection

Remove the cost of saying yes

Teams said yes once the implementation work wasn't theirs.

Retire your own work when the evidence says so

Sunk work is a poor reason to keep a product alive.
