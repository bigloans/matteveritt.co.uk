How I rank the backlog

I don't rank the spec's backlog by hand. I wrote the ranking rules down, and a script applies them to the issue register at the start of every working session, so the queue always follows the rules.

Seven rules, in order

The first rule an issue matches decides its rank. To change a priority, I move a rule up or down the list. The queue is built from that one list, so the queue and the rules can't disagree.

  1. 1An accessibility failure that reached production
  2. 2A gate check that reports a false verdict
  3. 3A blocker to a team adopting the spec
  4. 4A measured gate defect
  5. 5A measured spec gap
  6. 6A provable spec correction
  7. 7Provable tooling or governance work

A check that lies ranks near the top

A gate check that reports a pass it hasn't earned is worse than a missing check. A missing check is a known gap. A false pass tells a team their screen is fine when it isn't. Only an accessibility failure that has already reached production ranks higher.

Nothing is worked until it is proved

The queue only offers issues marked provable. Before anyone drafts a fix, the issue needs the measured label and a runnable reproduction in the issue itself. The script checks for both, because a label on its own is only a claim.

An accessibility failure in production is the one exception. Teams report it through a form, often without a reproduction, so reproducing it is the first piece of work.

The backlog today

Nothing open is an accessibility failure in production or a blocker to a team adopting the spec, which are two of the top three ranks.

Every open issue was filed by me or my agents, rather than reported by a team. Each defect gets its own issue, so review and test runs add them in batches. In one week in September, 15 arrived within 80 minutes. Since August, 661 issues have been filed and 464 closed. 93 of the 197 still open match a rule today.

It stops rather than guess

If the script can't read the whole register, it stops and writes nothing. A partial list ranked as if it were complete would hide work, and an out-of-date queue reported as current is worse than none. So a queue older than its time limit is never shown as today's.
