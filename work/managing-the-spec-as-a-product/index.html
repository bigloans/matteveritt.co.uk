Managing the spec as a product

I run the spec as a product, and I own its strategy, roadmap, backlog, releases and adoption. This read covers the product decisions behind it rather than the design system itself.

Framing the problem

The business problem was that the design system served a portfolio of 60+ products, but in six years only 6 had adopted it. I broke that down into four parts I could act on.

  • 3.5 weeks

    to build each component, because every one was built three times, in React, Vue and Angular

  • 1 person

    left to build them, once both team members moved on

  • 4 to 6 weeks

    of waiting while a central team built and released each component

  • Nothing

    told an AI coding agent what on-brand or accessible meant

I judged three options against five criteria: framework coverage, time to ship, drift control, maintenance cost and dependence on a central team. Keeping the library lost because one person would have built every component three times, for low adoption. Generating code from Figma lost because it generates from a picture, so the rules never reach the code. I chose the third option, a specification that teams' own agents build from, with a gate that checks the result.

Choosing it meant retiring my own work. 45 components were set aside, teams had only just migrated, and I had committed the old roadmap at CTO level. The case study covers what that pivot cost.

Testing the bet in stages

My hypothesis was that if AI agents generate every component, a design system needs no component library. It needs rules precise enough for a machine to follow and check. I tested it in four stages, and each stage asks a different question.

  1. Stage 1

    Can an agent build from it?

    Three fresh AI sessions built the same components from the pinned spec alone. All three failed on one button state no static check could see. I fixed the rule, and every release that changes a rule now gets this test.

  2. Stage 2

    Do teams get value?

    9 products are piloting it. Median time to a first gate pass is 2.5 days, down from 9 days for the first pilot to under 1 for the latest. A screen takes a median of 1.5 days, against 5 through the old handoff.

  3. Stage 3

    Do teams keep it?

    6 of the 9 are in production on a pinned release, so customers now use screens built from the spec. They include the AI agent and home hub, the entry point to every product.

  4. Stage 4

    Is the contract stable?

    Version 1.0 has six exit criteria and four are met. The first-run pass rate is 71% against a target of 75% over 100 builds, and the spec still needs one quarter with no token contract change. See the roadmap to 1.0.

Stage 1 was small, with three builds and one agent. It supported the method, but only adoption data could test the model, which is why the pilots matter most.

What teams told me

I learned what pilot teams needed in four ways. I held calls with them, watched them set up and build, read the issues they filed and reviewed their code and gate runs.

Most early adopters weren't building new UI. They had a shipping product, a chosen framework, global CSS and a designer with expectations. The same four problems came up, in the same order.

  1. The theme wasn't set

    A light product that didn't set the theme attribute rendered the dark values.

  2. Names clashed

    A product's own colour and spacing variables could share a name with the spec's, and the later one won without any warning.

  3. Themes crossed a boundary

    A dark panel inside a light product needs its own theme attribute, or it renders in the product's light values.

  4. Limits were unclear

    Teams needed to know what the spec doesn't govern, such as their existing UI and their global CSS.

So I wrote the guide for existing products first, and it names the four problems in the order teams hit them. Issues filed by later teams led to the setup fixes in recent releases, such as checkouts on Windows and setup outside GitHub.

What I did first, and why

Pilots before completeness

I argued rollout should wait until the component gap list closed. Then a smoke test found six contract defects that review had missed. I changed my mind, and pilots started with the first batch of components. They became the main way to find defects.

Existing products before new ones

Most early adopters had a shipping product, their own CSS and a designer with expectations. So I wrote the guide for existing products first. It names the four problems teams hit, in the order they hit them.

Do the first implementations myself

I built the first three implementations myself, so the early teams carried no cost. Later teams set themselves up with one command. Teams said yes once the implementation work wasn't theirs.

Day to day, a ranked queue decides what I work on next. How I rank the backlog shows the rules behind it.

Choosing the measures

North star

Products in production on a pinned release, counted weekly. It counts products that depend on the spec rather than what I ship, so a release nobody adopts doesn't move it. It stands at 6.

Time to market. Teams have filed 4 component requests so far. The first two took 14 days to reach a tagged release, and the latest two took 1 day. The old path waited 5 to 8 weeks for handoff, build and release.

Cost. Pilots built 144 screens. A screen took a median of 1.5 days against 5 through the old handoff, but that ratio comes from only 5 screens built both ways. If the pilot ratio holds across all 144 screens, the pilots saved about 500 engineering days.

Guardrail. Pinning protects teams from unplanned changes, but it also means a critical fix waits for each team to update. So I watch how long a critical fix takes to reach every adopter. Tagging one takes under 1 working day, and reaching the first three products took 6 working days. Every tagged fix now opens an automated pull request for each adopter. Teams still review and merge it, so the pin keeps protecting them.

Bringing leadership and teams with me

After the pivot I re-presented the roadmap at CTO level with new milestones. Engineering leadership then made the spec the default for new UI and reskins, with no mandate to rewrite existing screens.

Teams who had just migrated asked why they should redo work they had only just finished. Speed and cost changed their minds. In pilots a screen took a median of 1.5 days against 5 through the old handoff, and the first implementations cost the early teams nothing. Migrated teams also kept their assets, because the asset pipeline carried over intact, and they got a token mapping from the old system.

We love it, but we can't do it right now.

That was the outcome, so rollout follows each team's own roadmap. A funded reskin was what got teams moving. Mandates and demos converted nobody.

Reporting to leadership

I report progress with a weekly report generated from the issue register and the release tags, so every figure in it can be traced to its source. I also keep an implementation tracker that logs every contact and decision for each pilot team, so I can see each team's last contact, my next step and when to chase.

What I'd take to any product

Test by building, not by reading

I had only checked the spec by reading it. Building from it found a defect, and a smoke test found six that review had missed. A second smoke test found seven more before v0.97.0 shipped, so every release that changes the spec now gets one.

Remove the cost of saying yes

Teams said yes once the implementation work wasn't theirs.

Retire your own work when the evidence says so

Sunk work is a poor reason to keep a product alive.
